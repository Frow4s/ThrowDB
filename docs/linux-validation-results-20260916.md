# Результаты Linux-проверки от 16 сентября 2026 года

Проверена рабочая версия на основе `79fe6e4` с изменениями этого Linux-этапа.
Прогоны выполнялись в отдельном checkout и на одноразовых коллекциях.
Методика описана в [Linux validation](linux-validation.md).

## Среда и данные

Linux `6.1.0-42-amd64`, x86_64; GCC 13.3.0, CMake 3.28.3, Python 3.11.8.
Лимиты cgroup: квота, эквивалентная 10 CPU, и 256 GiB памяти.
Основной набор: 1 048 576 строк × 256 координат `float16`, то есть 512 MiB
полезных данных, с отдельным исходным массивом для побайтовой сверки.
Коллекция размещена в `/tmp` на OverlayFS; это не проверка прямого доступа к NVMe.

добавлены регрессии на граничные значения.

записи в pipe и повторяется прерванная `EINTR` запись.

## Python и изоляция тестов

Полный набор с настоящим native gRPC daemon выполнил 702 теста за 438,53 с:
696 прошли, шесть обнаружили ошибки в тестовых fixtures. Пять тестов калибровки
сочетали искусственные часы и читатель с живыми счётчиками Linux cgroup:
нагрузка других процессов делала результат недетерминированным. В этом fixture
теперь используется отдельный детерминированный resource probe.
Проверка отсутствия ID в workload-отчёте находила тестовый ID `202` в дате
каталога. Короткие ID заменены полными uint64 значениями; проверка всего JSON
сохранена. Рабочие resource guardrails и inspector не изменялись.

После исправлений прошли все 98 тестов калибровки и контроля ресурсов (3,59 с)
и все 67 тестов workload-журнала (2,89 с). Все шесть исходных ошибок закрыты.
Это покрывает первоначальные 702 теста успешным исходным либо повторным
прогоном, но не является одним чистым запуском `702 passed`.
Повторные наборы пересекаются с полным; складывать эти числа нельзя.

## Реальные backend'ы

Для pread (`thread_pool`, 0 workers), thread pool (4 workers) и io_uring
(2 workers, глубина 32) прошла побайтовая сверка 10 000 строк с исходным массивом.
Каждый отчёт содержит восемь последовательных и восемь конкурентных сценариев
`quick`, с cold/warm парами и 1/2/4/8 одновременными клиентами.
Фактический backend io_uring подтверждён и probe, и настройками открытой
коллекции; подмены на другой backend не было.

Ниже один сопоставимый срез: batch 1024, восемь клиентов, по 25 вызовов.

| pread | warm | 2 802 023 | 3,194 | 3,808 |
| thread pool, 4 workers | cold | 119 881 | 207,722 | 248,445 |

В этом cold-срезе `/proc/self/io` зафиксировал 498 655 232 / 499 531 776 /
503 017 472 байт чтения соответственно; в warm-срезе — ноль.

страниц файлов, а не глобальный сброс кэша. Эти короткие измерения на OverlayFS
не устанавливают универсального победителя и не обосновывают смену backend
по умолчанию.

## Реальный ENOSPC и восстановление

Оба сценария прошли за 1,65 с в приватных user/mount namespaces на `tmpfs`
с пределами **96 MiB и 16 384 inode**. Первый запуск с 64 MiB остановился ещё
при создании начальных 4096 partitions: их размещение с округлением до блоков
не оставило места для остальных файлов. Этот результат сохранён отдельно.

- **WAL append:** при оставшихся 4096 свободных байтах библиотека вернула
  `pwrite ... No space left on device`. WAL частично вырос с 5344 до 12 288 байт.
  Read-only reopen проигнорировал хвост; writable reopen усёк его до 5344 байт.
  Четыре подтверждённые строки и sequence 1 сохранились побайтово, неуспешная
  batch не стала частично видимой. Повтор завершился с 4096 строками и sequence 2.
- **Материализация:** библиотека вернула `write ... No space left on device`
  при записи staging-файла сегмента. Сохранились 4096 строк, sequence 1,
  один frozen WAL и отсутствие index runs. Generation увеличилась с 2 до 3
  из-за уже опубликованного резервирования ресурсов. Повтор опубликовал один
  run, освободил frozen WAL из текущего каталога и сохранил результат при reopen.

Filler-файлы удалены; после выхода namespace приватный mount исчез,
его внешний каталог пуст. Общая файловая система не заполнялась.

## Автоматическое обслуживание и wheel

Отдельный maintenance-сценарий прошёл **10/10 проверок за 1,43 с**.
Восемь durable upsert вызовов по четырём существующим строкам перевели
committed sequence с 0 на 8. Подтверждены rotation, materialization и folding;
после обслуживания frozen WAL, overlay и index runs отсутствовали,
materialized sequence равнялась 8. Количество строк, сверка четырёх выбранных строк с исходным массивом,
штатное завершение daemon и повторное открытие прошли успешно.

Собран `throwdb-0.1.0-cp311-cp311-linux_x86_64.whl` размером 9 153 869 байт.
Установка выполнена в отдельную `.wheelvenv`; smoke запускался с `python -I`
из `/tmp` и прошёл, включая CLI и упакованный gRPC-сервер.
Provenance подтверждает, что пакет, extension, native daemon и команды взяты
из `.wheelvenv`, source/editable hooks не использовались, версии совпали: `0.1.0`.
Это проверка wheel на данном Linux-хосте; совместимость manylinux не сертифицировалась.

`d0233c2dc3e2403cc92a7404aedb32a2cd5b0e06d2a6b5145220b8a5fcf17a72`.

## Mixed gRPC и два перезапуска

При клиентском бюджете 512 MiB первый запуск остановился после 48 Get:
528 752 640 байт рабочего RSS плюс резерв очередной stream batch превысили
лимит. Ошибок данных и RPC не было, но ни один перезапуск не состоялся.
Этот отчёт сохранён как неполный; успешные stream-флаги в нём не доказывают
прохождение SIGKILL.

Повтор с бюджетом 1024 MiB завершился успешно: 1200/1200 Get с побайтовой
сверкой исходного массива, все шесть сочетаний batch/prefix, CRUD и durable
replay, StreamGet и ScanRecords. Все acceptance и streaming gates прошли.
Два перезапуска выполнены: graceful (восстановление 0,810 с) и SIGKILL
(0,518 с). Подтверждены три поколения сервера и два ожидаемых прерывания
потоков при принудительном завершении. Подтверждённые записи повторены с теми
же токенами, idempotency domain сохранён, canary ID возвращены в отсутствующее
состояние. Неожиданных ошибок — ноль; финальные admission-ресурсы освобождены.

Сценарий завершился по лимиту 1200 Get за 5,18 с, передал 837 952 657 учтённых
байт; это короткая проверка mixed/restart, а не длительный soak. Исходные
границы: 90 с, 4 GiB передачи, 100 мутаций, 4 Get workers и 8 in-flight Get.
Пиковый RSS клиента — 690 638 848 байт; максимальная рабочая прибавка относительно
baseline — 626 630 656 байт. Fairness p99 ratio составил 2,422 при пороге 5.
Отдельные пороги роста RSS, FD и cgroup throttling не задавались: соответствующие
gate-флаги не подтверждают ограничения этих величин. Счётчики cgroup относятся
ко всей группе процессов. Прогресс maintenance доказан отдельным сценарием
выше, а не приписан этому короткому запуску.

ENOSPC на tmpfs проверяет ошибки записи и логическое восстановление, но не
power-loss или отложенные ошибки `fsync` на блочном устройстве. Набор 512 MiB
меньше доступной памяти. Короткие прогоны не заменяют длительный soak и работу
с данными больше RAM. S3 в этом этапе не проверялся.
