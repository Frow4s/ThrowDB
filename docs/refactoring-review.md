# Аудит и рефакторинг ThrowDB

Дата: 2026-09-04. Ветка: `codex/library-refactor`.

Исходная реализация взята из `codex/workload-aware-layout` (`a310204`) вместе
с незакоммиченными изменениями соседней рабочей копии. Их копия сохранена
отдельным коммитом `401ae6d`; собственно рефакторинг следует после него.
Исходная рабочая копия не изменялась. Это позволяет просматривать изменения
относительно `401ae6d`, не смешивая их с ранее начатой разработкой.

## Назначение и устройство

ThrowDB — дисковое хранилище векторов фиксированной размерности с точечным
поиском по числовому ID. Оно сохраняет float16/float32 без потери битов.
Это не реализация поиска ближайших соседей: индекса ANN и языка запросов нет.

| Слой | Ответственность | Существенный нюанс |
|---|---|---|
| Python `Collection`, pybind11 | Схема, NumPy, встроенные CRUD и потоки | Нормализация ID должна быть точной, а память потоков — ограниченной |
| `NativeCollection` | Выбор формата, снимки, совместимость | Старые форматы по-прежнему доступны читателям |
| Format 7, partitioned index | ID → RowRef, снимки разделов и immutable runs | Folding меняет индекс, cleaning переписывает живые строки одного сегмента |
| WAL и catalog/CURRENT | Долговечность и публикация состояния | Последовательность fsync/rename и блокировки являются частью контракта |
| Physical reader и scheduler | План диапазонов, чтение, scatter | pread — базовый путь; параллельные пути делят общий бюджет и DRR |
| `SingleCollectionEngine`, gRPC | Один серверный владелец коллекции, admission, replay | Повтор операции определяется ID, доменом и digest запроса |
| Tuning, workload logs, S3 | Измерения, наблюдение нагрузки, восстановление | Это отдельные bounded workflows; они не заменяют контракт хранения |

Новая коллекция использует формат 7. ID нормализуются в uint64; float16/float32
и размерность фиксированы для всей коллекции. Один процесс получает право
записи. Открытые читатели сохраняют снимок; чтобы увидеть изменения другого
процесса, дескриптор нужно открыть заново. Потоковые чтения удерживают свой
снимок и не должны превращаться в серию несогласованных unary-запросов.

Изменения сначала становятся долговечными в WAL. Materialization переносит
победившие записи ограниченного префикса WAL в сегменты и run индекса.
Partition folding сокращает слои индекса. Segment cleaning переносит ещё живые
строки выбранного сегмента. Orphan collection отдельно освобождает
недостижимые файлы, соблюдая возраст и бюджеты; старые читатели удерживают
открытые inode. Это разделение сохраняет короткую критическую секцию
публикации, но требует контроля свободного места и maintenance.

## Сильные стороны

- Согласованная модель долговечности: WAL, checksums, каталог поколений,
  writer lease, барьеры читателей и тесты аварийного восстановления.
- Формат 7 разделяет обслуживание индекса и перенос payload: не требуется
  переписывать всю коллекцию ради каждого цикла обслуживания.
- Ограниченные потоки и повторно используемые выходные буферы позволяют
  обрабатывать запросы, которые не помещаются в один RPC или массив RAM.
- Общий планировщик ограничивает суммарную конкуренцию чтений; маленькие
  запросы не обязаны ждать завершения всех диапазонов большого запроса.
- Tuning не запускается неявно при старте сервера. Сохранённый профиль
  проверяется относительно устройства, layout и reader ABI.
- Сервер использует тот же движок; проверки admission, pending-operation
  fence и отдельный журнал повторов явно моделируют сбои RPC.
- Обширные native/Python/crash-тесты позволяют менять внутреннее устройство
  без отказа от проверок совместимости и восстановления.

## Исправленные проблемы

### Одинаковые лимиты WAL при открытии и записи

Формат 7 проверял `max_wal_bytes` и `max_wal_operations` при открытии, однако
живой embedded writer мог выйти за них. Следующее открытие с теми же
параметрами тогда завершалось ошибкой. Заголовок ранее документировал более
строгий live-контракт только для формата 6; теперь поведение согласовано.

Общий `src/core/mutation_limits.hpp` учитывает каждый удерживаемый WAL,
включая frozen-файлы и пустые заголовки. Форматы 6 и 7 проверяют точный
прирост перед долговечной записью, а rotation — ещё и новый заголовок.
Автоматическая rotation учитывает первую транзакцию successor WAL.
Проверки используют вычитание из оставшегося бюджета, избегая переполнения.

Format-7 публикация резервирует overlay после проверки закодированной
транзакции: отклонённый по лимиту пакет не оставляет пустые зарезервированные
узлы и не расходует лимит следующих операций. No-op остаётся допустимым при
исчерпанном бюджете; maintenance может освободить удерживаемую квоту.

### Повторы RPC сохраняют исходный домен

Ранее каждое отправление брало домен из изменяемого кэша `Describe`.
После неопределённого результата, journal rollover и обновления metadata
тот же ID мог уйти в новый домен как новая операция.

`RemoteMutationToken` сохраняет UUID операции вместе с доменом. CRUD принимают
его в `operation_id=`, а `AmbiguousCommitError.retry_token` содержит именно
отправленную пару. Токен можно сохранить до запроса через `mutation_token()`
и использовать после переподключения. Переданные отдельно UUID/string/bytes
сохраняют исходный домен соединения даже после `describe()`/`count`.
Автоматически сгенерированный ID обозначает новую операцию и использует
текущий известный домен. Сервер отклоняет устаревший домен; автоматически
переносить неопределённую операцию в новый домен нельзя.

### Закрытие файлового дескриптора на Linux

`FileDescriptor::reset()` больше не повторяет `close()` при EINTR на Linux:
дескриптор уже мог быть освобождён и переиспользован другим потоком, поэтому
повтор мог закрыть чужой файл. Владение отсоединяется перед syscall.
Поведение других платформ сохранено. Основание — контракт
[Linux close(2)](https://man7.org/linux/man-pages/man2/close.2.html).
Регрессионный callback доступен только тестовым сборкам.

### Общая проверка ID и NumPy-буферов

`python/throwdb/_array_validation.py` объединяет нормализацию uint64,
ограниченное чтение последовательностей, проверку выходных массивов и
пересечения памяти. Убраны параллельные реализации из embedded/remote API.
Исправлены три расхождения:

- embedded source теперь обнаруживает изменение длины последовательности
  во время нормализации, как и remote source;
- подкласс ndarray не может скрыть пересечение входа и выхода через
  `__array_function__`; точная проверка ограничена по работе;
- маскированные выходные ID/locations отвергаются, поскольку нативная запись
  значений не обновляла их маску.

## Что удалено и упрощено

- Удалён внутренний TDBP/TCP transport: отдельный daemon, framing/protocol,
  Python-клиент и специфичные только для него тесты. Он не экспортировался
  публичным пакетом и не устанавливался. Общий движок, gRPC и его protobuf
  контракт сохранены. Полезные CRUD/Get/scan-проверки перенесены из TCP
  harness в прямой тест `SingleCollectionEngine`.
- `ServiceLimits` выделен в самостоятельный заголовок: gRPC больше не
  зависит от заголовков удалённого транспорта.
- Регистрация native-тестов вынесена в `cmake/ThrowDBTests.cmake` с одной
  функцией, явным списком целей и сохранением специальных gRPC/crash seams.
  Схема presets приведена к версии 2, совместимой с заявленным CMake 3.20.
- Версия задаётся только в `pyproject.toml`; CMake и pybind11 получают её
  оттуда. Изменение metadata инициирует повторную конфигурацию CMake.
- Native crash hooks компилируются только при `THROWDB_BUILD_TESTS=ON`.
  При обычной сборке пакета нет ни atomic-load callbacks, ни их объекта
  в статической библиотеке. Crash-тесты по-прежнему используют hooks.
- Обновлены инструкции по повторам RPC, лимитам, сборке и packaging.
  Fingerprint обновляющего скрипта теперь учитывает каталог `cmake/`.
- В gRPC CI добавлены Python E2E, benchmark smoke и mixed streaming soak
  с явно заданным нативным демоном: эти 13 проверок больше не пропускаются
  во всех стандартных Python jobs из-за отсутствия сервера.

## Что сохранено намеренно

- `Writer`/`Storage`, старые форматы и их тесты: это поддерживаемая
  совместимость и база сравнительных измерений, а не недостижимый код.
- pread, thread pool, io_uring и benchmarks: они сравнивают реальные
  альтернативы исполнения. Нельзя объявлять один backend лишним без
  измерений на целевой Linux/NVMe машине.
- WAL/catalog/CRC, S3 checksums, replay journal и pending fence: они решают
  разные задачи. Внешне похожие проверки не являются взаимозаменяемыми.
- Ограничители ресурсов, dry-run, orphan revalidation и crash-тесты:
  это часть корректности хранилища, а не отладочный шум.
- Документация старых форматов: нужна для чтения и диагностики существующих
  данных. Рефакторинг не требует миграции коллекций и не меняет байтовый формат.

## Ограничения и дальнейшие решения

`partitioned_index_storage.cpp`, `native_collection.cpp`, `_calibration.py`,
`workload.py` остаются крупными. Их механическое разбиение само по себе
не уменьшит связанность. Для следующего структурного шага нужны явные
интерфейсы владения snapshot/resources и фаз durable publication; переносить
их по файлам без этой границы опаснее, чем сохранять локальные инварианты.

Срок жизни снимков влияет на удержание RAM/файлов. Maintenance ограничен
по объёму, однако время уже начатого durable-действия ограничивается
кооперативно. Read-only snapshot не является автоматически обновляемой
репликой. Одна локальная коллекция и один writable server не обеспечивают HA.

Checksums на открытии не заменяют полный payload audit. Полная проверка,
backup/restore и измерения peak RSS на коллекциях рабочего размера остаются
дорогими отдельными процедурами. Prefix API само по себе не обещает
пропорционального уменьшения физических прочитанных байтов. Результат в
read workload log отражает обработку сервером; это не подтверждение доставки
ответа клиенту при сетевой отмене.

Лицензия, публикация артефактов, HA, application authorization, online backup,
ANN и новые типы ID — отдельные продуктовые решения. Они не добавлялись
под видом рефакторинга. Linux/io_uring и реальные NVMe/S3 нагрузки требуют
проверок в соответствующем окружении; локальные тесты не доказывают их
эксплуатационные характеристики.

## Проверка

Проверено локально на macOS ARM64: Python 3.10.13, AppleClang 15,
CMake 4.4.0, закреплённый native gRPC 1.81.0.

| Проверка | Результат |
|---|---|
| Исходный native-набор до рефакторинга | 29/29 программ |
| Release native после удаления TCP, `-Werror` | 28/28 программ |
| Полный `server-release`, `-Werror`, включая gRPC | 30/30 программ |
| ASan + UBSan, Debug | 28/28 программ |
| Полный Python-набор без готового native daemon | 720 passed, 13 skipped |
| Эти 13 пропущенных проверок после сборки daemon | 11 E2E + 2 benchmark/soak passed |
| Всего уникальных Python-тестов | 733 passed, без оставшихся пропусков |
| Wheel без сервера | Собран, установлен отдельно, CRUD/CLI smoke прошёл |
| Полный wheel с gRPC daemon | Собран, установлен отдельно, server smoke прошёл |
| Исходный sdist | Новые модули включены, удалённый TCP не включён |
| Presets, shell syntax, Python compileall, `git diff --check` | Успешно |

В wheel также проверены согласованность package/native version, наличие
нового модуля валидации и отсутствие старых TCP-модулей. Новая регистрация
CMake сохраняет все действующие native-тесты: удалён только TCP framing test,
а service test продолжает проверять движок напрямую. Изменения исходного
соседнего worktree после работы побайтно совпадают с сохранённым patch.

ASan/UBSan запускались с `detect_leaks=0`: macOS-проверка здесь не является
проверкой Linux LeakSanitizer. Linux-ветка регрессии `close(EINTR)` и реальный
io_uring остаются для Linux CI/целевой машины. Изменённый GitHub workflow
проверен локальными эквивалентами его команд, но сам удалённый CI не запускался.
Результаты не являются измерением production throughput, многосуточным soak
или проверкой восстановления настоящего S3-бэкапа.
