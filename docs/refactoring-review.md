# Аудит и рефакторинг ThrowDB

Дата: 2026-09-04. Ветка: `codex/library-refactor`.

Основа — `codex/workload-aware-layout` (`a310204`) вместе с последними
незакоммиченными изменениями её рабочей копии. Они сохранены отдельным коммитом
`401ae6d`; рефакторинг следует после него. Исходная рабочая копия не менялась.
Для просмотра только рефакторинга нужно сравнивать результат с `401ae6d`.

По решению владельца обратная совместимость не требуется. Теперь библиотека
создаёт и открывает **только формат хранения 7**. Читатели, писатели и кодеки
форматов 1–6 удалены; автоматической миграции и скрытого fallback нет.
Существующие коллекции формата 7 продолжают использовать тот же формат данных.

## Устройство и существенные нюансы

ThrowDB — дисковое хранилище векторов фиксированной размерности с точечным
поиском по числовому ID. Оно хранит float16/float32 без преобразования битов.
Индекса ближайших соседей, языка запросов и репликации в библиотеке нет.

| Слой | Ответственность | Существенный нюанс |
|---|---|---|
| Python `Collection`, pybind11 | Схема, NumPy, встроенные CRUD и потоки | ID нормализуются точно; потоки проверяют опасное пересечение NumPy-буферов |
| `NativeCollection` | Проверка текущего формата, владение, публичный фасад | Делегирует операции единственному partitioned движку |
| Partitioned index | ID → RowRef, immutable snapshots/runs и WAL overlay | Folding обслуживает индекс, cleaning переносит payload |
| WAL, catalog и CURRENT | Долговечность и публикация состояния | fsync/rename, порядок блокировок и pending-operation fence — часть корректности |
| Physical reader и scheduler | План диапазонов, чтение, scatter | Backend работает в общем бюджете конкуренции и справедливого обслуживания |
| `SingleCollectionEngine`, gRPC | Серверное владение, admission, replay | Повтор определяется UUID операции, доменом и digest запроса |
| Tuning, workload logs, S3 | Измерения, наблюдение нагрузки, восстановление | Это самостоятельные процессы с ограничениями ресурсов |

ID покрывают весь диапазон uint64. Dtype и размерность фиксированы для
коллекции. Писатель один; открытый читатель удерживает согласованный снимок.
Чтобы увидеть публикации другого процесса, читатель открывается заново.
Потоковые чтения также удерживают один снимок, включая состояние overlay.
Дескрипторы привязаны к создавшему процессу и не используются после `fork()`.

Изменения сначала фиксируются в WAL. Materialization переносит победившие
записи ограниченного префикса frozen WAL в сегменты и run индекса. Partition
folding сокращает слои индекса. Segment cleaning переносит живые строки
выбранного сегмента. Orphan collection отдельно удаляет недостижимые файлы,
соблюдая возраст, бюджет и повторную проверку достижимости. Барьер открытия
читателей защищает гонку между чтением каталога и открытием его файлов;
читатели, уже открывшие ресурсы, удерживают inode после unlink.

## Плюсы реализации

- Явные гарантии долговечности: WAL, checksums, поколения каталогов, writer
  lease, reader barrier и тесты аварийного восстановления.
- Обслуживание индекса отделено от переноса векторов. Не требуется копировать
  всю коллекцию при каждой materialization или cleaning.
- Ограниченные потоки и выходные NumPy-буферы подходят для запросов, которые
  не помещаются в один RPC или массив RAM.
- Общий планировщик ограничивает конкуренцию чтений и не заставляет маленький
  запрос ждать завершения всех диапазонов большого запроса.
- Tuning запускается явно. Сохранённый профиль проверяется относительно
  устройства, layout и reader ABI до выбора параметров чтения.
- Сервер использует тот же движок; admission, журнал повторов и pending fence
  моделируют неопределённый результат RPC и восстановление после сбоя.
- Набор native/Python/crash-тестов проверяет наблюдаемое поведение и позволяет
  существенно сокращать код без отказа от проверок восстановления.

## Что удалено и упрощено

- Удалены immutable `Writer`/`Storage` из C++, pybind11, Python и type stubs.
  Встроенный Python API использует `Collection` и её builder;
  удалённый доступ остаётся в `RemoteCollection`.
- Удалены старый flat index, storage reader/writer, native manifest старых
  форматов, delta codec/catalog/inventory и ветки совместимости в фасаде.
  `native_collection.cpp` сокращён примерно с 4100 до 1000 строк.
- Python `Collection`, CLI, remote `Describe`, calibration/device discovery
  и benchmark runner теперь используют только актуальный layout. Старые
  варианты `format_version` отклоняются до создания коллекции.
- Убраны всегда нулевые метрики открытия старого flat index и недостижимые
  классы orphan-файлов. Действующие метрики partitioned reader сохранены.
- Удалены benchmark runners и документы исключительно для старых форматов.
  Проверки их кодеков удалены; полезные проверки публичного фасада перенесены
  на формат 7: снимки, lease, fork, WAL recovery, validation и reader barrier.
- Удалён внутренний TDBP/TCP transport: отдельный daemon, протокол, Python
  клиент и framing-тесты. gRPC, protobuf и общий серверный движок сохранены.
  Полезные service-проверки выполняются напрямую через движок.
- `ServiceLimits` выделен в самостоятельный заголовок. Native-тесты
  регистрируются общей CMake-функцией с явным списком целей.
- Версия пакета задаётся в `pyproject.toml`; CMake и pybind11 берут её оттуда.
  Presets используют схему 2, совместимую с заявленным CMake 3.20.
- Crash hooks компилируются только с `THROWDB_BUILD_TESTS=ON`; устанавливаемый
  daemon не содержит специальных subprocess hooks даже в тестовой сборке.
- В gRPC CI добавлен запуск Python E2E, benchmark smoke и streaming soak
  с явно заданным нативным daemon, чтобы эти тесты действительно выполнялись.

Версии внутренних структур независимы от версии коллекции: manifest v2,
catalog v3, WAL v1, protobuf v1 и версии workload logs используются текущим
форматом 7. Они не являются оставшимися читателями старых коллекций.
Публичные имена API приведены к этим структурам на следующем этапе,
описанном ниже; прежние имена не сохранены как aliases.

## Исправления корректности

### Одинаковые лимиты WAL при открытии и записи

Ранее формат 7 проверял `max_wal_bytes` и `max_wal_operations` при открытии,
но работающий embedded writer мог выйти за них. Повторное открытие с теми же
параметрами тогда завершалось ошибкой.

Общий `mutation_limits.hpp` учитывает все удерживаемые WAL, включая frozen
файлы и пустые заголовки. До durable write проверяется точный прирост; rotation
учитывает новый заголовок, а автоматическая rotation — и первую транзакцию
successor WAL. Проверки не переполняют счётчики. Отклонение по лимиту WAL
не оставляет пустых зарезервированных overlay-узлов. No-op допустим при полном бюджете;
maintenance может освободить удерживаемую квоту.

### Повторы RPC сохраняют исходный домен

Раньше повтор мог взять новый домен из изменённого кэша `Describe` после
journal rollover. Та же неопределённая операция рисковала стать новой.

`RemoteMutationToken` сохраняет UUID вместе с доменом. CRUD принимают токен
через `operation_id=`, а `AmbiguousCommitError.retry_token` содержит именно
отправленную пару. `mutation_token()` позволяет сохранить её до запроса.
Отдельно переданные UUID/string/bytes сохраняют исходный домен соединения;
автоматически сгенерированные ID новых операций используют текущий известный
домен. Сервер отклоняет устаревший домен, не переносит повтор автоматически.

### Проверка ID и NumPy-буферов

`_array_validation.py` объединяет нормализацию uint64, ограниченное чтение
последовательностей, проверку выходных массивов и пересечения памяти.
Embedded и remote API используют одну реализацию. Исправлены изменение длины
последовательности во время нормализации, обход overlap-проверки через
`ndarray.__array_function__` и приём маскированных выходных ID/locations,
маску которых нативная запись не обновляет.

### Файловые дескрипторы и lifecycle fence

`FileDescriptor::reset()` больше не повторяет `close()` при EINTR на Linux:
дескриптор уже мог быть освобождён и переиспользован другим потоком. Владение
отсоединяется перед syscall. Основание — контракт
[Linux close(2)](https://man7.org/linux/man-pages/man2/close.2.html).

При удалении старого фасада проверки pending-operation fence перенесены в
актуальный partitioned reader. Materialization, folding, cleaning и orphan
reclaim сохраняют защиту незавершённой durable RPC; dry-run остаётся чтением.
Порядок блокировок и существующие idempotency-регрессии сохранены.

## Минусы и оставшиеся ограничения

Сложность сосредоточена в `partitioned_index_storage.cpp`, `_calibration.py`
и `workload.py`. Следующий обоснованный структурный шаг — выделение контрактов
владения snapshot/resources и фаз durable publication. Простое распределение
функций по файлам не уменьшит связанность и затруднит проверку инвариантов.

Снимки удерживают RAM и файлы. Maintenance ограничен по объёму, но дедлайн уже
начатой durable операции проверяется кооперативно. Нужны свободное место и
явная политика обслуживания. Одна локальная коллекция с одним писателем
не обеспечивает HA; read-only snapshot не является обновляемой репликой.

Проверка checksums при открытии не заменяет полный payload audit. Prefix API
не обещает пропорционального уменьшения физических прочитанных байтов.
Workload log фиксирует серверную обработку, а не доставку ответа клиенту.

pread, thread pool, io_uring и действующие benchmarks сохранены: это реальные
альтернативы исполнения, выбирать между ними нужно по измерениям целевой
машины. Производительность Linux/NVMe, настоящие S3 backup/restore, peak RSS
на рабочих объёмах и длительный soak не доказываются локальными unit-тестами.
Лицензия, application authorization, HA, online backup, ANN и новые типы ID
остаются отдельными продуктовыми решениями.

## Уточнение публичного API — 2026-09-05

Имена C++, Python, CLI, protobuf diagnostics и benchmark reports теперь
описывают текущий partitioned layout. Это намеренно несовместимое изменение
API: aliases старых имён отсутствуют. Формат существующих коллекций 7 и байты
хранимых векторов не меняются.

| Прежнее имя | Текущее имя и смысл |
|---|---|
| `shard_size_bytes`, `--shard-size-gib` | `segment_size_bytes`, `--segment-size-gib`: целевой размер immutable сегмента |
| `compact_deltas()`, C++ `compact_delta_runs()`, CLI `compact-deltas` | `fold_partitions()`, CLI `fold-partitions`: сведение полных разделов индекса в snapshots |
| Параметры `compact_*`, CLI `--compact-*` | `fold_*`, `--fold-*`: бюджеты и пороги partition folding в maintenance |
| `delta_run_count`, `delta_entry_count`, `total_delta_run_bytes` | `index_run_count`, `index_run_entry_count`, `index_run_bytes`: удерживаемые immutable runs |
| `delta_put_rows`, `total_delta_segment_bytes`, `total_delta_bytes` | `materialized_segment_rows`, `materialized_segment_bytes`, `mutation_resource_bytes`: строки и объём materialized ресурсов |
| `compacted`, `compacted_delta_input_entries`, `compacted_delta_input_bytes`, `compaction_budget_blocked` | `folded`, `folded_run_input_entries`, `folded_run_input_bytes`, `fold_budget_blocked`: результат и затраты одного fold |
| `zero_delta_fast_path` | `snapshot_only_fast_path`: чтение без активных index runs и WAL overlay |

Удалены метрики, оставшиеся от несуществующих веток lifecycle:
`catalog_managed`, `delta_managed`, `reclaimed_wal_count`,
`reclaimed_wal_bytes`, `compacted_delta_run_count`,
`reclaimed_delta_run_count`, `reclaimed_delta_bytes`.
Реальные результаты orphan collection и показатели folding остаются в своих
отчётах. Maintenance action теперь называется `fold_partitions`.

Примеры создания, embedded maintenance, CLI и installed-wheel smoke обновлены
вместе с API. Историческая таблица от 4 сентября выше относится к предыдущему
этапу. Ограниченный сценарий для настоящего Linux/io_uring и mixed restart
приведён в [Linux validation](linux-validation.md); наличие сценария само по
себе не означает, что он выполнен. Результаты текущего этапа фиксируются
отдельно по фактическим проверкам.

Убрано оставшееся ограничение `max_runs >= 2`: folding принимает бюджет от
1 до 4096 runs на выбранный partition. Snapshot в это число не входит.
Если у partition два активных runs, бюджет 1 оставляет его без изменения;
частичное сведение раздела не разрешается. Это проверяется через C++, Python,
CLI и автоматическое серверное обслуживание.
